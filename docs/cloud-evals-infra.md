# Cloud evaluation lane — infrastructure and worker host

Companion to [`cloud-evals.md`](./cloud-evals.md), which is the normative
contract between the three implementations. This document covers the half that
document deliberately left open: **how the worker is packaged, how it is
invoked, and what about that is proven versus assumed.**

Everything here concerns `server/promptatron/worker/`, the
`AWS::BedrockAgentCore::Runtime` resource in `api/template.yaml`,
`scripts/package-eval-worker.sh`, and `make deploy-worker`.

## Where the facts came from

Two tiers, kept separate on purpose, because they do not deserve equal
confidence.

**Read directly, in this repository's own dependency tree** — the strongest
evidence available without an AWS account, since it is the service model the
SDK actually validates against:

- `botocore/data/bedrock-agentcore-control/2023-06-05/service-2.json`
  (botocore 1.43.69, vendored in `server/.venv`) — the AgentCore *control plane*:
  `CreateAgentRuntime`, `AgentRuntimeArtifact`, `CodeConfiguration`,
  `AuthorizerConfiguration`, `LifecycleConfiguration`.
- `botocore/data/bedrock-agentcore/2023-06-05/service-2.json` — the *data plane*:
  `InvokeAgentRuntime` and its header/shape constraints.
- `bedrock_agentcore/runtime/app.py` and `runtime/models.py` from
  **bedrock-agentcore 1.21.0** on PyPI — the SDK's actual HTTP contract and
  async-task behaviour, read as source rather than inferred from docs.
- `/workspace/readysetcloud/rsc-core/template.yaml` — a working
  `AWS::BedrockAgentCore::Runtime` CodeZip deployment (Node), which is what
  makes "CodeZip works in CloudFormation" a fact rather than a hope.

**Second-hand, from AWS documentation via search** — `docs.aws.amazon.com` is
blocked by this environment's egress proxy, so these were read as search
summaries, not fetched pages. Treat them as strong hints, not verified:

- [Direct code deployment for Python](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-code-deploy-python.html)
  — zip layout, dependency vendoring, the `uv pip install --python-platform` recipe, arm64-only.
- [Handle asynchronous and long running agents](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-long-run.html)
  — the async task pattern and the idle-session interaction.
- [AgentCore quotas](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html)
  — 100 MB payload, 250 MB zipped / 750 MB unzipped artifact, 8 h maximum.

Each claim below is tagged **[model]**, **[sdk]**, **[rsc]** or **[docs]**
accordingly.

## Decision: CodeZip, not a container image

The worker ships as an **S3 zip artifact** (`CodeConfiguration`), not an ECR
container image (`ContainerConfiguration`).

`AgentRuntimeArtifact` is a union of exactly those two **[model]**, so this is a
real fork in the road, and the zip side wins on every axis that matters here:

- **It is proven in CloudFormation.** rsc-core deploys a `NODE_22` CodeZip
  runtime through `AWS::BedrockAgentCore::Runtime` today **[rsc]**. The Python
  path differs only in the `Runtime` enum value and the entry point's file
  extension — `AgentManagedRuntimeType` accepts `PYTHON_3_10`, `PYTHON_3_11`,
  `PYTHON_3_12`, `PYTHON_3_13`, `PYTHON_3_14` and `NODE_22` **[model]**.
- **This repository has no container toolchain.** `api/` builds Node Lambdas
  with esbuild; there is no Dockerfile, no buildx, no ECR repository, and no CI
  step that could produce a cross-architecture arm64 image. Adding one to ship a
  pure-Python worker would be the largest single piece of new machinery in the
  change.
- **`uv` already does the hard part.** The one genuinely awkward requirement —
  arm64 wheels built on an x86 laptop — is a flag, not a build system:
  `uv pip install --python-platform aarch64-manylinux_2_28 --target …
  --only-binary=:all:`.

The cost is that the artifact carries its own dependency tree (56 MB zipped,
196 MB unzipped, against a documented 250 MB / 750 MB ceiling **[docs]**), and
that a new dependency means a rebuild rather than a `pip install` at boot. Both
are fine at this size; see [Open risks](#open-risks) for the headroom.

### What the zip looks like

```
agentcore_app.py          <- EntryPoint; a shim, generated by the packaging script
promptatron/              <- the application (copied from server/, pure Python)
bedrock_agentcore/        <- the SDK
strands/ boto3/ …         <- every other dependency, as aarch64 wheels
```

`CodeConfiguration.entryPoint` is a list of 1–2 strings, each at most 128
characters **[model]**; AWS's Python examples pass a single `.py` filename
**[docs]**, and rsc-core passes a single `index.js` **[rsc]**. We pass
`agentcore_app.py`.

The root `agentcore_app.py` is deliberately a four-line shim over
`promptatron.worker.agentcore_app`. It both re-exports `app` and calls
`app.run()` under `if __name__ == "__main__"`, which covers both plausible host
behaviours — executing the file as a script (what rsc-core's `app.run()` at
module scope implies **[rsc]**) or importing it and looking for an `app`. See
[Open risks](#open-risks).

### Building it

`scripts/package-eval-worker.sh`:

1. `uv export --frozen --no-dev --extra worker --no-emit-project` — the locked
   dependency set, including `bedrock-agentcore` from the new `worker` extra in
   `server/pyproject.toml`. `promptatron` itself is excluded and copied in
   directly: it is pure Python, so there is no wheel to cross-build.
2. `uv pip install --python-platform … --python-version 3.12 --target …
   --only-binary=:all:`. The `--only-binary` is a safety net, not an
   optimisation: a source distribution would compile for the *build* machine's
   architecture and fail at import inside the arm64 runtime. Failing the build
   is strictly better than failing at 3 a.m. in a cold start.
3. Zip under a **content-hashed key**, `eval-worker/<sha256[:16]>.zip`.

#### `manylinux_2_28`, not `manylinux2014`

AWS's example recipe uses `--python-platform aarch64-manylinux2014` **[docs]**.
That fails for this dependency set: **greenlet ≥ 3.3** (pulled in by SQLAlchemy
via SQLModel) no longer publishes `manylinux2014` (glibc 2.17) aarch64 wheels —
only `manylinux_2_24`/`manylinux_2_28`. Verified empirically: the build errors
with `No solution found … greenlet==3.5.5 has no usable wheels`.

`manylinux_2_28` is safe because AgentCore's managed runtimes are Amazon Linux
2023 based (glibc 2.34). The floor is overridable via
`EVAL_WORKER_PYTHON_PLATFORM` if that ever turns out to be wrong.

#### Why the key is content-hashed

This is rsc-core's hard-won lesson, applied to Python **[rsc]**:

> Prefix MUST change when the artifact changes […]. A static Prefix means CFN
> never rolls this runtime and it serves a stale bundle.

AgentCore reads the zip when the runtime is created or updated. CloudFormation
only issues an update when a property it can *see* has changed — and the S3 key
is the only property that reflects the code. Upload new bytes under the same key
and CloudFormation correctly concludes nothing changed, leaving the old bundle
serving forever. Hashing the content makes every real code change a visible
property change, and makes a no-op deploy genuinely a no-op.

The build is reproducible (normalised timestamps, sorted zip entries), so the
same source really does produce the same key.

## Invocation: fire-and-forget over a synchronous API

`InvokeAgentRuntime` is `POST /runtimes/{agentRuntimeArn}/invocations` and
returns a streaming response **[model]**. There is no asynchronous-invoke
variant — no `InvocationType: Event`, no queue. "Fire and forget" is therefore a
property of *the application*, not of the API.

The worker's entry point is `promptatron.worker.agentcore_app.dispatch`:

1. Validate the envelope `{evaluation_id, request}`.
2. Write `EVAL#{id}/META` as `pending`, then `running`.
3. `asyncio.create_task(…)` the evaluation.
4. Return `{"status": "accepted", …}`.

FastAPI's `InvokeAgentRuntime` call therefore returns in roughly the time of two
DynamoDB writes, and progress is read from DynamoDB from then on, exactly as
`cloud-evals.md` specifies.

### `@app.async_task` does not do what its name suggests

This is the single most important thing to get right, and the docs' framing is
misleading. From the SDK source **[sdk]**:

```python
def async_task(self, func):
    async def wrapper(*args, **kwargs):
        task_id = self.add_async_task(func.__name__)
        try:
            result = await func(*args, **kwargs)   # <- awaits. Does not defer.
            return result
        finally:
            self.complete_async_task(task_id)
```

The decorator **awaits** the coroutine. Decorating the entry point with it would
make the invocation block for the whole evaluation — the opposite of what is
wanted. Returning fast is the application's job: `dispatch` calls
`asyncio.create_task` itself.

What the decorator *is* for is health reporting, and that part is load-bearing.
`get_current_ping_status()` returns `HEALTHY_BUSY` whenever `_active_tasks` is
non-empty, and `GET /ping` serves it **[sdk]**:

```python
current_status = PingStatus.HEALTHY_BUSY if self._active_tasks else PingStatus.HEALTHY
```

A runtime session idle for 15 minutes is terminated **[docs]**, and after the
invocation returns there are no in-flight requests — so without a tracked task
the session reads as `Healthy` (idle) and can be reaped mid-evaluation. The
worker therefore applies `@app.async_task` to the *background job*, not the
entry point:

```python
_tracked_execute = app.async_task(execute)   # keeps /ping at HealthyBusy
...
spawn(_tracked_execute(evaluation_id, request, store))   # returns immediately
```

`add_async_task(name)` / `complete_async_task(task_id)` are the manual
equivalents **[sdk]**; the decorator is the same thing with a `try/finally`.

### Session ids

`runtimeSessionId` travels in the
`X-Amzn-Bedrock-AgentCore-Runtime-Session-Id` header and is typed `SessionType`:
**min 33, max 256** **[model]**.

Evaluation ids are 32-character uuid4 hex — *always exactly one character
short*. `promptatron.worker.interfaces.session_id_for()` is the single place
that pads them (`{evaluation_id}-promptatron-eval`, 49 chars); the FastAPI
invoker should import it rather than re-deriving the rule. It is deterministic,
which also matters because `runtimeSessionId` is modelled as an idempotency
token **[model]** — a retried invoke lands on the same session instead of
starting a second one.

The padding stays inside `[a-zA-Z0-9][a-zA-Z0-9-_]*`, the charset the *response*
side's `SessionId` shape declares **[model]**.

### Limits worth knowing

| Limit | Value | Source |
|---|---|---|
| Request/response payload | 100 MB | **[docs]** |
| `runtimeSessionId` length | 33–256 | **[model]** |
| Artifact zip | 250 MB zipped / 750 MB unzipped | **[docs]** |
| Idle session timeout | 900 s default (60–1 209 600) | **[model]** |
| Session max lifetime | 28 800 s / 8 h default (60–1 209 600) | **[model]** |
| Environment variables | 50 | **[model]** |
| `AgentRuntimeName` | `[a-zA-Z][a-zA-Z0-9_]{0,47}` — no hyphens | **[model]** |

The 8 h default ceiling is the real bound on a single evaluation. At 25 runs
maximum (`evals.schemas.MAX_RUNS`) with three concurrent, that is not close to
binding; if it ever became so, `LifecycleConfiguration.maxLifetime` raises it to
14 days **[model]**.

## Inbound auth: IAM, by omission

`AuthorizerConfiguration` is a union whose **only** member is
`customJWTAuthorizer` **[model]**. There is no "IAM authorizer" object to
configure — IAM (SigV4) is what you get when the property is absent, and a
runtime is JWT- *or* IAM-authorized, never both **[rsc]**.

`api/template.yaml` therefore omits `AuthorizerConfiguration` entirely. That is
the right choice here: the only caller is the FastAPI server, which already
holds AWS credentials, and unlike rsc-core there is no browser opening a socket
directly to the runtime. The server needs `bedrock-agentcore:InvokeAgentRuntime`
on the runtime ARN.

### Execution role

`EvalWorkerRole` grants only what the evaluation actually does:

- `s3:GetObject` on the artifact bucket — reading the CodeZip.
- `bedrock:InvokeModel*` / `bedrock:Converse*` on foundation models and
  inference profiles — the model under test and the judge.
- `bedrock:ApplyGuardrail` — guardrail-backed runs.
- `dynamodb:GetItem` / `PutItem` / `UpdateItem` on the existing table. Notably
  **no `Query` and no `Scan`**: the worker only ever touches items whose keys it
  already knows. Querying is the reader's job, and the reader is the FastAPI
  server with its own credentials.
- Logs, X-Ray, and `cloudwatch:PutMetricData` scoped to the
  `bedrock-agentcore` namespace.

The trust policy is `bedrock-agentcore.amazonaws.com` with both
`aws:SourceAccount` and `aws:SourceArn` conditions (rsc-core uses
`SourceAccount` alone **[rsc]**; the `SourceArn` narrowing is free).

## Deploying

The worker is **opt-in**. `EvalWorkerArtifactKey` defaults to `''` and the
`DeployEvalWorker` condition gates the runtime and its role, so the config-store
stack deploys exactly as it did before.

```
make deploy-worker
```

does the whole thing: bootstraps the stack if the artifact bucket does not exist
yet, builds the artifact, uploads it under its hashed key, deploys with
`EvalWorkerArtifactKey` set, and prints the runtime ARN with the two environment
variables the server needs.

```
PROMPTATRON_EVAL_RUNTIME_ARN=arn:aws:bedrock-agentcore:…:runtime/promptatron_eval_worker-…
PROMPTATRON_EVAL_TABLE=promptatron-config-ScenariosTable-…
```

`make package-eval-worker` builds the artifact alone and makes no AWS calls.

### One sharp edge

`deploy-worker` is a **superset** of `deploy-api` — same stack, plus the
runtime. Once the worker exists, keep using `deploy-worker`: a bare
`make deploy-api` passes no `EvalWorkerArtifactKey`, the parameter falls back to
its empty default, and CloudFormation deletes the runtime. This is inherent to
plain CloudFormation parameters with defaults; the alternatives (SSM-backed
parameters, or persisting the value into `api/samconfig.toml`) both add moving
parts, so the mitigation is a loud comment on the parameter, in the Makefile,
and here.

### Config store access

If evaluations reference stored scenarios/prompts/datasets, the worker needs the
config store's API key. CloudFormation cannot read an
`AWS::ApiGateway::ApiKey`'s value, so it is passed in:

```
EVAL_WORKER_CONFIG_API_KEY=$(aws apigateway get-api-key \
    --api-key <ApiKeyId output> --include-value --query value --output text) \
  make deploy-worker
```

## The worker's two seams

### To the evaluation engine

`promptatron/worker/interfaces.py` is the whole surface between the host and
`promptatron.evals`:

```python
async def run_evaluation(request: dict, emit, store, cancelled) -> EvalOutcome
```

It resolves `promptatron.evals.engine.execute_evaluation_with_seam` **lazily**,
at call time. Two things depend on that: the worker had to import cleanly while
the evals refactor was still in flight, and an AgentCore cold start should not
pay to import the run engine (boto3 clients, strands, SQLModel) before an
invocation has arrived. `test_importing_the_worker_does_not_import_the_evals_engine`
pins it down in a subprocess.

The engine's seam takes a validated `EvaluationRequest`, so `parse_request`
bridges the wire JSON to the model — which keeps the worker from re-implementing
(and drifting from) the eval schema. `normalize_outcome` accepts either the full
`{status, result, error, run_ids}` envelope or a bare result dict, so a
misbehaving or older engine still reaches a terminal state rather than hanging
the evaluation at `running`.

### To DynamoDB

`promptatron/worker/ddb.py` implements the engine's `EvalStore` protocol
(`save_evaluation`, `load_run`, `save_run`) plus the emitter and cancel polling.
Two of `cloud-evals.md`'s writer rules are enforced *structurally* rather than
by convention:

**Terminal status is never visible before the result.** `finalize()` writes
`status`, `result`, `error` and `run_ids` in a single `UpdateItem`. There is no
item version in which a reader sees `status="completed"` and no `result`.

**`eval_complete` is always the last event.** The engine settles the row and
*then* publishes:

```python
seam.store.save_evaluation(status=status, result=result, error=error)
seam.publish(EvalCompleteEvent(status=status, result=result))
```

Written straight through, that order opens exactly the race the reader cannot
tolerate: the reader stops polling on terminal status, so an event appended
*after* the flip can be missed. So a terminal `save_evaluation` is **buffered**,
and flushed by `emit()` the moment `eval_complete` is durable — or by
`finalize()` with a synthesized `eval_complete` if the engine died before
publishing one. The engine does not have to know any of this.

### Two contract clarifications for the reader

`cloud-evals.md` leaves these slightly open; the writer resolves them as
follows, and the FastAPI reader must match.

1. **`META.run_ids` is a JSON *string*, not a native DynamoDB list** — decoded
   with the same `json.loads` as `config` and `result`. This matches the SQLite
   `evaluations.run_ids` TEXT column and the row's JSON-as-string convention
   throughout.
2. **Nullable fields are written as `NULL`, never omitted.** Every attribute the
   contract declares is always present on the item, so the reader never has to
   distinguish "absent" from "null".

The writer also adds one attribute the contract's table does not list:
`META.progress` (a JSON string, `{completed, failed, total}`), because the
engine writes it mid-flight and the SQLite lane has the column. Readers may
ignore it.

## Open risks

Mirroring rsc-core's "verify on first deploy" list. Everything here is
unverifiable without an AWS account, and this branch has none.

**Packaging and boot**

- **`EntryPoint: agentcore_app.py`.** cfn-lint 1.52.1 (bundled with SAM CLI
  1.165.0) ships **no schema at all** for `AWS::BedrockAgentCore::Runtime` — the
  `providers/*/aws-bedrockagentcore-*.json` files simply do not exist — so
  `sam validate --lint` cannot check a single property on this resource. The
  literal is unvalidated; confirm it against a real deploy.
- **How the entry file is loaded.** Executed as a script, or imported? rsc-core's
  `index.ts` calls `app.run()` at module scope, implying execution **[rsc]**.
  The generated shim handles both, but if AgentCore imports the module and
  expects a specific symbol name other than `app`, this needs adjusting.
- **`manylinux_2_28` floor.** Chosen because greenlet forced it and AL2023 has
  glibc 2.34. If the runtime image turns out to be older, `_greenlet`/`pydantic_core`
  will fail at import; `EVAL_WORKER_PYTHON_PLATFORM` is the escape hatch.
- **Artifact size.** 56 MB zipped / 196 MB unzipped against 250 MB / 750 MB
  **[docs]**. Comfortable, but `sympy` (30 MB, via `strands-agents-tools`) and
  `pillow` (23 MB) are pure dead weight for an eval worker. If the ceiling is
  ever approached, prune those first — nothing in the evaluation path imports
  them.
- **Cold start.** Unmeasured. The import graph is large (strands, boto3,
  OpenTelemetry) and the worker acknowledges *after* two DynamoDB writes, so the
  first invocation after a deploy will be materially slower than steady state.

**Runtime behaviour**

- **Survival of the background task.** The design rests on `asyncio.create_task`
  outliving the HTTP response inside AgentCore's uvicorn process. This is
  ordinary ASGI behaviour and `@app.async_task` keeps `/ping` at `HealthyBusy`
  to hold the session open — but "the microVM is not frozen or reclaimed between
  requests while a task is tracked" is precisely the thing only a real
  long-running evaluation can prove.
- **Whether `HealthyBusy` actually defers the idle reaper.** The mechanism is
  documented **[docs]** and implemented **[sdk]**; the interaction is not
  verified.
- **`!GetAtt EvalWorkerRuntime.AgentRuntimeArn` / `.AgentRuntimeId`.** Chosen
  because `CreateAgentRuntimeResponse` returns both fields **[model]**, but with
  no cfn-lint schema the attribute names are unverified. rsc-core sidesteps this
  by constructing the ARN with `!Sub` over `!Ref` **[rsc]**; if the `GetAtt`
  fails at changeset creation, that is the fallback.
- **The `s3:GetObject` grant's timing.** The role is read by AgentCore when the
  runtime is created. CloudFormation should order role-before-runtime from the
  `!GetAtt EvalWorkerRole.Arn` dependency, but IAM propagation delay has been
  known to make the first create flaky; a retry is the usual fix.

**Correctness under real DynamoDB**

- The DynamoDB tests run against a hand-written fake
  (`server/tests/fake_dynamodb.py`) covering exactly the operations the writer
  emits. It models no consistency, capacity, or throttling behaviour, and it
  raises rather than guessing on any expression form the writer does not
  currently produce. The *item shapes* it captures are the contract and are
  worth trusting; anything about DynamoDB's own semantics is not.
- **Conditional writes.** `begin()`'s `attribute_not_exists(pk)` and
  `mark_running()`'s status guard are exercised against the fake's
  reimplementation of those conditions, not against DynamoDB.
- **`ConsistentRead` on the cancel flag.** Correct by construction, but the race
  it closes (DELETE returns 204, worker starts one more run) has not been
  observed either way.
